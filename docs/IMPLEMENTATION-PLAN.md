# Bayer: план и исходный аудит

Исходная ревизия: см. `git log`. Production не изменяется.

P0: убрать автоматический каталог (форма и trigger); сохранить ссылки image_path существующих товаров; защитить UTC created_at; версионировать подтверждения и снимки; атомарные RPC с RLS и блокировками; очередь удаления Storage; плановые деньги отделить от платежей.
P1: единый редактор новых/существующих черновиков, IndexedDB с Blob, последовательная обработка изображений, идемпотентные id, optimistic concurrency; авто/авиа со снимком тарифа; заметки и квитанции; закупка по product_id, частичные количества.
P2: cron с lease и повторами, orphan sweep, обезличенные помесячные агрегаты; браузерные проверки WebKit/Chromium; README и release checklist.

Обнаружено:
- `orders/new/page.tsx` откатывает весь заказ после ошибки; фотографии только в React state; сохранение в каталог дублирует SQL trigger.
- `buyer_submissions.order_id UNIQUE` запрещает историю согласований; прежнее подтверждение не содержит заметок/фото/параметров закупки.
- `buyer_finance_summary` суммирует частично известные величины и подписывает ожидание как заработок; учёта оплаты нет.
- soft-delete бессрочный; срок и Storage GC отсутствуют; signed URL на клиенте не обновляются.
- публичный API ограничивает body, но не частоту запросов; квитанция при повторном открытии отсутствует.

Решения: SQL — авторитетная денежная валидация; TS — предпросмотр той же формулы, проверяемый тестами. Историческая цена без исходной закупки сохраняется до явного ввода закупки. Повторное согласование сохраняет прежние снимки, закупки привязаны к стабильному product_id и не копируются. Пересогласование запрещено после завершения, уменьшение выбора ниже уже закупленного/отменённого запрещено. Перед удалением production-каталога обязателен внешний backup; миграции сначала проверяются на копии. Постоянного архива товаров не создаётся.
