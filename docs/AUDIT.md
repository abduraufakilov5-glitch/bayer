# Аудит Bayer — 20 сентября 2026

## Область проверки

Проверен исходный код репозитория: все страницы кабинета и клиента, авторизация/выход, конфигурация Next.js и PWA, ценообразование, типы, обе исходные SQL-миграции, Storage/RLS, зависимости и GitHub Actions. Добавленный API проверен отдельно. Рабочая база, её реальные политики, серверные журналы и настройки хостинга не инспектировались. Следовательно, это аудит репозитория и локально воспроизводимых сценариев, а не подтверждение безопасности всей рабочей инфраструктуры.

## Архитектура

Next.js App Router обслуживает серверную проверку авторизации и страницу публичного заказа. Кабинет обращается в Supabase из браузера с publishable key, поэтому RLS — основная граница доступа. Клиентский заказ получает данные через Supabase Edge Function; подтверждение выполняется PostgreSQL-функцией в транзакции. Фотографии хранятся в приватном бакете. Финальная цена сохраняется в товаре заказа, а при подтверждении копируется в позиции заявки.

Для небольшого кабинета это понятная архитектура. Главные риски исходной версии находились в целостности заказа, воспроизводимости установки и обработке ошибок, а не в выборе фреймворка.

## Новые пользовательские возможности

1. Поиск заказов по названию и номеру (`#00012`), комбинируемый со статусом и сортировкой.
2. CSV всей отфильтрованной выборки и подтверждённого состава. Имена защищены от spreadsheet formula injection.
3. Клиентский поиск и просмотр только выбранных товаров.
4. Корзина с сохранением на устройстве по токену заказа; удалённые позиции и некорректные количества не восстанавливаются.
5. Детальная проверка состава перед подтверждением и квитанция с номером, количеством и суммой после отправки.
6. Безопасная повторная отправка после сетевого сбоя.

## Проверки и границы доказательств

- `npm run check`: ESLint, TypeScript, 10 тестов проходят.
- PGlite выполняет всю цепочку миграций: два владельца не видят данные друг друга; anon не читает таблицы и не вызывает RPC; опубликованные товары неизменяемы; запрещены пропуски статусов; ошибочные подтверждения не создают заявки; повтор не создаёт дубль; сумма снимается с серверных цен.
- API-тесты проверяют валидацию до доступа к БД, ограничение тела, принадлежность путей фото, публичные поля, конфликты и сокрытие внутренних ошибок.
- 8 браузерных прогонов (4 сценария × desktop/mobile): корзина/перезагрузка/поиск/dialog/ошибка/повтор/успех; login/dashboard/CSV/детали/logout; 404/защищённые страницы; добавление из каталога/пустая цена/rollback/retry.
- `npm run build`: production-сборка проходит без ключей рабочей базы. Локальная песочница блокировала внутренний порт Turbopack; сборка прошла после разрешения запуска процессов и очистки ошибочного кеша.
- Визуально проверена страница клиента: содержимое есть, горизонтального переполнения и Next.js error overlay нет.
- `npm audit` после обновления: 0 известных уязвимостей на дату проверки.

Браузерный Supabase — HTTP-макет. База тестируется отдельно на настоящем PostgreSQL-движке PGlite с тестовыми схемами Supabase. Это не проверка настоящей Supabase Auth/Storage/Edge-среды, параллельных транзакций отдельными соединениями, Safari или доставки писем. Supabase Advisors рабочего проекта не запускались; нет настроенного подключения к нему.

## Оставшиеся ограничения и дальнейшее развитие

- **Большой каталог.** Кабинет каталога пока получает один набор данных и создаёт отдельную signed URL на каждый товар. Следующий шаг — серверная пагинация, пакетная подпись ссылок и загрузка фото по мере прокрутки. Список заказов уже обходит ограничение одной страницы Supabase, но для десятков тысяч заказов тоже нужен серверный поиск.
- **Курс и доставка.** Курс 1,4 и тариф 30 TJS/кг фиксированы. Настройки байера с сохранением параметров в каждом заказе позволят менять тарифы без пересчёта старых заказов.
- **Атомарное создание.** База и Storage не имеют общей транзакции. При потере сети или закрытии вкладки в момент загрузки очистка может не завершиться. Для следующего этапа нужны серверная сборка черновика, ключ повторной попытки и периодическая очистка незавершённых загрузок.
- **Сроки ссылок.** Фото действуют час; корзина сохраняет только количества и требует перезагрузки для обновления изображений. Публичный токен не имеет срока действия/отзыва; следующий этап — отдельное отозвание ссылки и журнал действий.
- **Защита от массовых запросов.** Ограничения размера/количества и UUID-токены добавлены, но распределённого rate limiting для Edge Function пока нет.
- **Фотографии.** Нет автоматического сжатия, конвертации HEIC, проверки содержимого файла и восстановления загрузок. Ограничения 8 МБ и 300 товаров нужно учитывать на телефоне.
- **PWA.** Иконки и standalone manifest есть; service worker, offline-режима и push-уведомлений нет.
- **Бизнес-функции.** Нет клиентских контактов, оплаты, частичных поставок, комментариев, уведомлений Telegram и финансовой аналитики. Поле `telegram_notified_at` само по себе не означает реализованную отправку уведомлений.
- **Рабочая инфраструктура.** Перед выпуском проверить реальные миграции, резервное копирование, Auth signup, журналы ошибок, RLS/Storage policies и Advisors на тестовом проекте.
