## Безопасность

- RLS всех новых таблиц включён. Покупки/платежи/месячные суммы доступны только владельцу; оперативные таблицы недоступны anon/authenticated.
- Привилегированные RPC явно проверяют `auth.uid()` и владельца, используют пустой search_path. Подтверждение/очистка/квота доступны только service_role. Trigger-функции не имеют EXECUTE у клиентских ролей.
- Публичный API не отдаёт CNY, supplier_url, себестоимость, прибыль или owner_id отдельными полями. Signed URL всё равно содержит путь Storage и является временной capability-ссылкой.
- Публичная ссылка UUID случайна; отзыв/ротация и истечение срока проверяются на сервере. Уже выданные signed URLs не отзываются до удаления файла/истечения срока (до часа).
- Блокировка заказа сериализует изменение/публикацию/подтверждение. Идентификаторы закупок стабильны между версиями. Уменьшить подтверждение ниже закупленного количества нельзя.
- Очередь удаления и новые ссылки на файлы синхронизированы advisory locks. Очистка проверяет продукты и снимки всех заказов. Добавлены индексы для срока, FK и путей изображений.
- Неизвестные FK каталога останавливают миграцию: `DROP` без `CASCADE`. Тест проверяет rollback и сохранность чужой зависимости.

## Проверки и честные границы

Локально выполняются lint, TypeScript, production build и 28 unit/API/PostgreSQL тестов. Есть проверки SQL/RLS, повторов и конкурирующих вызовов, границы 25 суток, общих файлов, финансовых агрегатов и обновления старой схемы.

Браузерные тесты — 9 сценариев × Chromium desktop, Chromium iPhone, WebKit iPhone = 27. [Прогон 38775105395](https://github.com/abduraufakilov5-glitch/bayer/actions/runs/38775105395) прошёл полностью. Расширенный набор и последующие исправления проверяются отдельным финальным прогоном; его ссылку фиксирует итоговый отчёт. В прогоне 38775828140 один WebKit упал до загрузки `/orders/new` с внутренней ошибкой движка, остальные 17 прошли; это не выдаётся за успешный прогон.

Браузеры обращаются к настоящему PGlite PostgreSQL/RPC через локальный HTTP-адаптер Supabase. Auth и Storage transport тестовые. Это проверяет цепочку UI→API→SQL→UI, но не заменяет запуск на реальном staging Supabase. Локальные прямые Playwright-запуски блокируются песочницей macOS до загрузки страниц; CI на Linux запускает оба движка. Через встроенный браузер дополнительно пройдены выбор/заметки/подтверждение, кабинет и частичная закупка при ширине 390 px.

`npm audit --omit=dev`: 0 уязвимостей после обновлений. Полный audit: 5 high записей в одной цепочке ESLint→fast-glob→micromatch→braces, для текущего инструмента нет безопасного patch-исправления. Это инструменты разработки, не код публичного API. Автоматический downgrade Next.js ради audit не применялся. [Исходная уязвимость Next.js](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j).

Реальные Auth expiry, Supabase Storage/gateway, физический iPhone, работа системного меню установленных мессенджеров и отправка в настоящий Telegram требуют staging-приёмки. Установка cron и secrets в production — отдельный согласуемый выпуск по `docs/RELEASE.md`.

Корректировки фактических затрат записываются в `buyer_purchase_events` как неизменяемые дельты с RLS владельца. Проверено, что доначисление в следующем месяце сохраняет прежние расходы в исходном месяце; агрегирование при удалении использует тот же журнал.
