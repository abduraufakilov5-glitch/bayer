# Безопасный выпуск

Изменения не применялись к production. Не запускайте новую миграцию на рабочей базе без отдельного согласования. Она удаляет таблицу каталога и меняет контракты RPC.

1. Ограничить запись старой версии приложения на время переключения. Сделать внешний PostgreSQL backup всех `buyer_*` и проверяемую копию bucket `buyer-product-images`. Не включать таблицы других приложений. Проверить восстановление на отдельном проекте. Временный backup удалить после принятого срока восстановления; приложение не создаёт скрытый архив.
2. На восстановленной копии выполнить `docs/preflight.sql`: проверить FK/внешние зависимости, целостность snapshot/image_path, объекты Storage. Уже существующие order products имеют собственные ценовые поля и image_path; миграция сохраняет их без пересчёта, включая общие фотографии. Копирование файлов не требуется: shared paths удерживаются живыми ссылками всех заказов и снимков. Если текущая production-схема отличается от миграций — остановиться и сначала согласовать diff.
3. Применить миграции по имени, начиная с отсутствующих. Новая: `20261015163021_reliable_order_workflow.sql`. `DROP TABLE` намеренно без `CASCADE`: неизвестная внешняя зависимость должна остановить выпуск. Не выполнять `db reset` на связанном production.
4. Проверить на staging реальные Supabase Auth (включая истечение сессии), Storage upload/sign/delete и Edge Function `buyer-public-order`; две независимые вкладки подтверждения; новый/старый заказ; HEIC iPhone. PGlite не заменяет эти проверки инфраструктуры.
5. Развернуть Edge Function и согласованную Next.js версию вместе: старый POST без revision совместим только с первой версией; открытые старые страницы после пересогласования получают 409 и должны обновиться.
6. Только после отдельного одобрения выполнить production-релиз. Настроить серверные `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET` (не менее 32 случайных байтов), `NEXT_PUBLIC_SUPABASE_URL`, публичный ключ, `BAYER_ADMIN_URL`; для Telegram — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_BUYER_ID`. Service role никогда не передаётся в браузер.
7. В Vercel проверить активный cron `/api/maintenance` из `vercel.json` (ежедневно, 01:15 UTC), ручной защищённый прогон на staging и журнал `buyer_job_runs`. Cron без secrets отвечает 401/503; отсутствие успешных запусков >26 часов — инцидент, нужна внешняя проверка мониторинга. Ошибки Storage остаются в очереди с backoff; следующая задача их повторит. Можно безопасно вызывать задачу дополнительно, lease ограничивает конкуренцию.

## Удаление

Публичный API закрывает доступ точно при `created_at + 25 суток`. Физическое удаление запускается ежедневно, поэтому фактическая задержка зависит от расписания (до суток при нормальной работе). Пакеты: 50 заказов, до 20 пакетов/запуск, до 50 пакетов по 100 файлов; есть временной лимит. При необычном большом backlog запустить дополнительные защищённые прогоны или увеличить частоту на тарифе Vercel, который это допускает. Уже выданный signed URL может действовать до удаления файла/истечения его срока (до часа); отзыв ссылки не отзывает ранее скачанные фотографии.

Сначала транзакция агрегирует только деньги по owner/month, ставит фотографии в очередь и удаляет заказ с каскадами. Затем worker удаляет только неиспользуемые файлы через Storage API. Частичный отказ не возвращает публичную ссылку и не теряет очередь. Остатки незавершённых загрузок без ссылок собираются после 24 часов. Это окно позволяет безопасно повторить сохранение с iPhone.

## Финансы

План учитывает только актуальную подтверждённую версию. Полученные деньги — отдельный журнал с UUID операции (повтор не создаёт платёж). Реальная закупка = цена CNY × фактический курс × купленное количество + фактическое карго всей позиции + дополнительные расходы. Неизвестная составляющая даёт неизвестную сумму, а не ноль. Фактическая прибыль не считается окончательной, пока выбранные позиции не закуплены/отменены. План уменьшается для отменённых единиц, исходная клиентская квитанция сохраняется. Возвраты и expense_refund записываются отдельными движениями. Фактическая прибыль — денежный результат после внесённых расходов и возвратов; не записанный возврат не появляется автоматически. Нельзя одновременно заносить один расход и в закупку, и в общий журнал.

## Ограничения

- Браузер может очистить IndexedDB; локальная копия не является заменой серверному сохранению. Несохранённые файлы восстанавливаются на том же устройстве/профиле.
- Редактор сохраняет весь набор товаров атомарно. Другая вкладка получает конфликт версий, а не перезаписывает свежие изменения.
- HEIC декодируется динамически загружаемой библиотекой; повреждённые/неподдерживаемые варианты отклоняются с повтором/удалением. Физический iPhone и современные варианты HDR/HEIF требуют staging-проверки.
- Telegram: повторная доставка at-least-once, при потере ответа Telegram возможен дубль; ошибка не откатывает подтверждение. В ежедневной задаче обрабатывается до 10 ожидающих уведомлений; для частой доставки нужны более частые защищённые прогоны.
- Системное меню WhatsApp/Telegram зависит от установленных приложений и браузера.
